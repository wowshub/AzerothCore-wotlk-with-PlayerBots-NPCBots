# WD144A：把“能显示”做到“能保存并生效”

这是候选实现的教学，不是游戏已成功的证明。源文件在01目录，原样测试在checks，生成工具在tools；有讲解的文档不能覆盖游戏。

## 1. 先分清四个号码

节点ID像天赋面板的商品编号，SpellID像实际效果的零件编号，index像存档的格子编号，bit_offset像该格子在通信数据里的起始位置。它们不能混用。例如节点1969有两个等级，对应9003990和9003991，index114占offset126起的2位。2位可以表示0、1、2、3，但天赋只有两级，因此3必须被拒绝。UI允许点亮不等于数据库能保存。

本轮把同一份nodes.csv生成C++、Lua和布局哈希，避免手工写三份而偏移。双级各占2位，单级各占1位：126+2+2+1+1=132位，十六进制长度132/4=33。容量仍为256，只增加实际占用；旧索引绝不重排。

## 2. 先让效果范围精确，再接原生计算

实际C++（Support144.inc）核心条件：

```cpp
if(mod->spellId==Arrow1||mod->spellId==Arrow2)
    return !(mod->op==SPELLMOD_COOLDOWN&&check->Id>=9003970&&check->Id<=9003978);
```

第一行确认“是哪一个天赋在修改”；第二行同时确认“修改冷却”及“目标是恶毒箭等级链”。本项目该钩子的false表示命中，故最外面取反；这和很多函数true代表成功的习惯相反，必须读调用方。SpellInfo.cpp还给这四个修饰被动加入阻止宽匹配的分支，否则白名单未命中后仍可能掉回职业mask匹配。课堂知识点是布尔代数、白名单和控制流，而不是只记一段if。

强化冷却用原生107平面修饰、op11，量为-2000/-4000毫秒。DBC的EffectBasePoints通常存实际值减1且DieSides为1，所以-2000要存-2001的32位表示；不要把秒直接写进去。

洛阿之力用79（学校伤害百分比）、misc40=8自然|32暗影；第二效果137（总属性百分比）、misc1=敏捷，值3/6。普通物理伤害可能因敏捷变化间接受益，这和“原生3/6%学校加成只限自然/暗影”不是同一件事。判断时要控制装备和角色属性，不能拿所有伤害都不动当验收条件。

## 3. 为什么迟钝诅咒要补两个零值效果

天赋像调音旋钮，只有旋钮没有声道，调再大也不会有声音。旧9003150只有第0槽减速。本轮给第1槽308（对施法者的暴击加成）、第2槽259（受到的周期治疗百分比）补零值声道。未选天赋两者都是0；巨蛇用op12把第1槽加10，腐朽用op23把第2槽减30。不是改第0槽减速，也不是把所有治疗统一打七折。

本地Unit.cpp已有原生处理：308检查诅咒的caster GUID是否为当前攻击者；259在周期治疗分支使用。因此用原生规则，不在每次伤害/治疗后再乘一次，避免双算。上游场景只证明其中一部分，故本地还读取了对应原生路径；最终仍必须用游戏日志测试。

## 4. 方案变化还要照顾已经挂出去的诅咒

```cpp
Aura* aura=target?target->GetAura(Jinx,p->GetGUID()):nullptr;
if(AuraEffect* e=aura->GetEffect(EFFECT_1)) e->ChangeAmount(Owns(p,Serpent)?10:0);
if(AuraEffect* e=aura->GetEffect(EFFECT_2)) e->ChangeAmount(Owns(p,Decay)?-30:0);
```

第一行按法术ID和本人GUID定位，不拿别人同名诅咒；调用这段前实际代码检查aura为空则移除失效追踪并continue。第二、三行只更新对应附效，Owns同时检查已学技能和本人光环。效果量设为0并不等于删除整个诅咒，原减速仍在。容器存GUID而非长期裸指针，是为了目标消失后重新查询；找不到目标就清除失效记录。死亡、跨图和离开视野的真实行为仍需验收。

被动两级不是自动等级链：Apply先移除不该保留的6个私有被动，再学当前级并补光环，最后刷新旧诅咒。这样从一级升二级不会3%+6%=9%。这涉及拥有权、对象生命周期及事件回调，不只是DBC写数字。

## 5. SQL为什么出现“一级成功、二级失败”

保存过程按node_def接受rank2，但原表CHECK_3还写着旧多级节点白名单。数据库最后一层约束比界面更严格，INSERT触发异常后整次保存回滚。不能为了通过而去掉所有约束；正确做法是从同一节点定义生成每个节点最大等级CASE，新添1969/7779为2，其余旧规则不变。ID与rank约束在同一ALTER里换，迁移前先拒绝未知/未来映射。

```sql
CHECK(node_rank BETWEEN 1 AND CASE node_id
  WHEN 1969 THEN 2 WHEN 7779 THEN 2
  -- 实际交付SQL还包含所有原有多级节点，不要用此教学片段覆盖。
  ELSE 1 END)
```

SQL还核对等级、专精、预算、父节点、互斥、revision及不能免费退点。旧wd67save会转给新版校验；不能因旧整数表示不了新节点就先删后保存。数据库知识点是约束、事务、幂等迁移和乐观并发控制。

## 6. 测试为什么分几层

- test_listener.lua实际加载插件，覆盖点击、掩码、保存协议及版本不匹配锁定；曾抓到旧TE分类把暗影误判巫毒。
- test_allocation.cpp抽取实际校验代码，用2万组旧布局对比旧结果，再检查四个新节点；证明旧规则未意外变化，不能证明游戏伤害。
- test_mod_scope.cpp枚举4个修饰来源、1001个目标ID、32个操作，即128128组合；合法的必须命中，其他必须不命中，也单独排除普通75。
- test_mysql144.py启动独立33544实例并核对datadir，跑301条真实SQL断言：包含rank2保存、重复安装、rank3拒绝、旧单级上限保留、旧写入不能抹新节点、互斥与费用、World冲突时不写入。finally负责关测试实例。
- DBC验证读回每个字段和字符串偏移，确认旧表除9003150外所有行原样、字符串旧前缀保留；两端分别验证，不能因为名字一样就混用。
- MSVC /Zs只做语法检查，不生成新游戏EXE，也不证明链接和服务器运行。

工具使用Python3.9处理CSV/JSON/WDBC、StormLib只读MPQ、Lupa Lua5.1执行插件逻辑、隔离MySQL8验证持久化、MSVC检查实际C++。tools保留本轮研究脚本，仍依赖工作区基线与wd19_common/wd9a_storm等本地辅助模块，不是给用户部署时运行的安装器。
