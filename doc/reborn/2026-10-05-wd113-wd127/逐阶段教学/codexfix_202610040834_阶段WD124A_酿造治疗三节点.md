# WD124A 从官方天赋到本项目方案的逐步说明

先分清四类编号：35065/35064/35068 是官方天赋节点 ID，705862/705860/705861/705865 是官方 Spell ID，9003897–9003900 是本项目新建的私有 Spell ID，而 93–96 是方案保存掩码中的位。不能把节点 ID 当技能 ID，也不能用官方 Spell ID 直接覆盖本项目 DBC。

## 1. 从官方资源确定“选了什么”

`research/official_nodes.json` 摘取官方 2026-09-25 `CharacterAdvancementData.json` 的三个 Brewing 节点和 Spell 对应关系。`research/official_spells.json` 留存 patch-T.MPQ Spell 行。药师有两个 Spell，所以节点是两级；药水投手和再生者各一级。所有节点要求先有 8 点基础酿造 TE，每级再花 1 TE。同层三个新节点不能互相凑门槛。

## 2. 让角色方案可靠保存

`01_覆盖到源代码根目录/modules/mod-reborn-witchdoctor/src/RebornWitchDoctorAllocation.inc` 的前十行把新节点放在数组末尾，并把药师放在两位的 94–95 位。第 47–51 行验证高位、药师最大二级与 8 点基础酿造 TE；第 125–127 行在收到节点及 rank 后生成准确高位。客户端 `Allocation.lua` 第 59–80 行用同一位表、预算和级数验证；第 405–407 行给三个节点分别显示描述。服务端 `server_SQL/01_CHARACTERS_WD124A_必须执行.sql` 第 144–146 行用 DECIMAL 精确解出三个新 rank；第 259–261 行写入节点行。如此保存、重登和方案切换读回的数值才一致。

## 3. 从“已保存”转成真正的被动

`RebornWitchDoctorAllocation.inc` 第 162–174 行只按当前激活方案选择 9003897–9003900：药师一级要求 rank==1，二级要求 rank==2，不会同时授予两个回蓝 Aura。取消选择时先移除旧 Spell/Aura，再为当前方案学习并补上缺失的 Aura。这样重登后属性可恢复，换方案后旧效果不会残留。

双端 `Spell.dbc` 各自追加四个原生被动 Spell。药水投手是 Aura107（SpellMod cooldown，-5000 毫秒），药师是 Aura134（施法中法力回复）与二级的 Aura136（治疗量），再生者是 Aura220（精神折算法术暴击等级）。DBC BasePoints 需写“目标数值减 1”；比如 50% 写 49、10% 写 9，负 5000 毫秒写负 5001。此差一问题已在交付前校正。旧 Spell 行没有修改。

`RebornWitchDoctor.cpp` 第 3013–3015 行只让药水投手修饰 9003870–9003876 的药水投掷，以及 9003890–9003896 的泼洒药水。核心 `SpellInfo.cpp` 第 1420 行把该私有 ID 纳入精确匹配分支，阻止空家族掩码把减冷却误作用到所有技能。技能书条目追加在两端 `SkillLineAbility.dbc`；药师一级指向二级的替代关系，与旧两级被动的做法一致。

## 4. 为什么再生者写“等级”而非固定暴击百分点

目标核心 `PlayerUpdates.cpp` 的 `Player::UpdateRating` 会对 Aura220 按精神算出 CombatRating，并写进 `CR_CRIT_SPELL`；之后 `StatSystem.cpp` 再依人物等级把等级转换成暴击几率。因此官方“精神的10%”并不代表暴击率恒定加10个百分点。实测时看法术暴击等级更可靠。

## 5. 本轮验证与实机边界

`tools/scenario124.lua` 检查旧方案场景、97位边界、药师非法三级、预算/专精/门槛与精确保存字符串；`tools/test_mysql.py` 在专用 33500 端口临时 MySQL 测 449 项，不接触生产库；`tools/validate_wd124.py` 比较双端 DBC 旧行、四个新被动、SkillLineAbility 与所有字符串偏移。Lua 全量语法检查通过。C++仍由用户编译，真实冷却、回蓝、治疗、属性和客户端显示必须在游戏内确认。不要把静态检查写成实机通过。
